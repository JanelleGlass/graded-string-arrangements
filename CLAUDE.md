# Graded String Arrangements (website)

Janelle's free public website: hymns and carols arranged for violin, viola, cello and bass in
levels from open strings to advanced (four levels and three voices; songs built before 2026-10-16
have six levels), each with a play-along reader. A few simple pieces have no levels: one line, the
same for each instrument it is for (Twinkle Harmony, 2026-10-21). Janelle is a Suzuki strings teacher, not a
programmer: tell her what changed on the page, not in the code.

- Live: https://graded-string-arrangements.vercel.app
- Repo: https://github.com/JanelleGlass/graded-string-arrangements (public: never commit anything
  that isn't meant for the website, such as PDFs for sale, scans, or her build tools)
- Hosting: Vercel, connected to this repo. **A push to `main` goes live by itself in about a
  minute.** So push only when Janelle has seen the change and said to.
- Vercel builds each commit once. A commit already pushed on another branch (a Claude working branch gets a
  Preview) is skipped when the same commit then reaches `main`, so the site doesn't change (2026-10-21, and
  probably the "Vercel missed the previous push" on 2026-10-17). To go live from a working branch, put a new
  commit on `main` (`git merge --no-ff`), not a fast-forward, and check Vercel's Deployments list shows it as
  Production.

This folder normally sits inside her `Music Arrangements` folder (as `website/`), where the
arrangements are built. Arrangement rules live in `../BUILD-SPEC.md`, not here.

Commands (on Janelle's Windows PC use `python`; elsewhere `python3`):

    python tools/build_site.py
    python tests/smoke.py
    python tests/sight_reading.py
    python tests/listening.py

The test checks the Parts panel on the first 24-part and the first 40-part song in `songs.json`,
on the first 34-part song (or, with none, the 40-part song's score cut to 34 parts), on the
first piece with no levels (one line), and on the first song with a Piano part.

The whole test takes about twelve minutes (eight songs, 2026-10-23), a little more with each song, and says how
long it took. Run it with no time limit (a Claude session: in the background). A limit that stops it part-way (a
`timeout`, or the 10-minute limit on one command) closes its browser, and Playwright then reports "Page crashed" or
"Target crashed" in whatever step was running. That looks like the reader crashing, but it isn't: on 2026-10-23 three
runs stopped that way at 9 min 50 s, in Joy to the World's Concert checks, and passed with no limit.

In a Claude cloud session the network may block cdn.jsdelivr.net (2026-11-02): then every song page fails "page
loads (TimeoutError)", the reader never having got alphaTab. Fetch the same file from npm and point the test at it:
`npm pack @coderline/alphatab@1.8.4` in the scratchpad, untar `package/dist/alphaTab.min.js`, and run the test with
`ALPHATAB_JS=<that path>`. Python's Playwright there must match the browser already installed (`pip install
playwright==` the version `node -e "console.log(require('playwright/package.json').version)"` prints). The Play
together library (supabase-js, also from jsdelivr) can't load there either, and the piano check counts the failed
download as a script error ("silent-night: no script errors: ... ERR_TUNNEL_CONNECTION_FAILED", twice; 2026-11-12):
that is the session's network, not the site. Play together on a slow or patchy connection: `node tests/together_sim.js`
(see "Play together on the website").

The test needs Playwright once per computer: `python -m pip install playwright` then
`python -m playwright install chromium`. To look at a page yourself: `python -m http.server 8000`
in this folder, then http://localhost:8000/ .

## Adding a song

Only after Janelle has checked the finished arrangement in the Music Arrangements folder.

1. Copy the finished file to `songs/<slug>/<slug>.xml` (slug: lowercase-with-dashes, e.g.
   `holy-holy-holy`). Copy only the finished arrangement (the 40-part file, with its Countermelody, Concert and
   Piano parts when it has them), nothing else from her folder. Convert it to LF line endings first: the files in her
   folder are often CRLF, and the build fingerprints raw bytes. A solo piece goes on only when Janelle asks for that
   piece (Morning Has Broken's two solo viola Variations went on 2026-10-23 and were taken off again at Janelle's
   request on 2026-11-12, their folders deleted; git history has them): its XML only, as one line, with its part
   renamed from `Viola` to `Viola — Solo` in the site copy so the build reads it, then colored and fingered with her
   `add-colors-fingerings.py` (her solo files are plain, and the reader's finger looks need fingerings; that tool
   writes CRLF, so convert to LF again). Its PDF stays private.
2. Add the song to `songs.json` (title, section on the home page: Christmas, Hymns, Solos (a piece for one player)
   or Other; category, a small label on its card, or "" where it would only repeat the section; collection, source
   line, `pdf_url` empty until there is a Payhip link). A new section goes in `SECTIONS` in `tools/build_site.py`.
3. Run the build. It reads key, time, bars and the written tempo from the score, and stops unless the
   parts are one of the layouts the reader knows, named and ordered as in BUILD-SPEC section 3:
   40 parts in levels and voices (level by level; Melody, Inner, Bass Line; violin, viola, cello,
   bass), the same 40 then a Countermelody on violin and viola and/or a Concert part on each (42 or 44),
   34 in the same with no cello or bass Inner (built 2026-10-16), or 24 in the old six tiers
   (level by level; violin, viola, cello, bass), or one line (a piece with no levels: one to four
   parts, violin to bass, each named "<instrument> — <the line's name>"), or a duet (`<instrument> — Part 1`, then
   `<instrument> — Part 2`: the sight-reading duets' layout). It says which one it read. Tell Janelle what it read so she can catch a mismatch. It also
   adds the song to the offline copy (`sw.js`), so installed copies get it on their next open.
4. Run the test. Show her the page (local server, laptop and phone sizes) before pushing.
5. Commit and push when she says go. Then check the live page loads.

## Changing the reader

1. Edit `reader/reader.html`.
2. Build, then test. For anything visual, also take screenshots at laptop (1366x860), phone
   landscape (844x390, 667x375 for iPhone SE) and phone portrait sizes, and look at them.
3. Update the Claude preview: publish `reader/reader.html` as an artifact to
   https://claude.ai/artifact/WqVvah4mND1xSPHvPpybTv (pass that URL so it updates in place).
   Don't change its capabilities: it uses the `room` capability for the conductor. Its score,
   font and sound files are already published there and are kept. The preview plays the
   four-level First Noel, so publish a copy of the reader with its two "six levels" lines (the
   meta description and the About box) worded as the build words them for a song in levels and voices; the
   master reader keeps "six levels" because the build swaps those lines song by song. In that copy the Print
   button is `hidden` too: Claude's preview window can't open a print dialog.
4. Push when Janelle says go.

If a reader change touches one of the song-specific strings the build swaps out (title, About box
facts, `SCORE_URL`, `BASE_TEMPO`, `TEMPO_PERCENT`, the storage key, the Buy-note line, the title wrapper), update
`TEMPLATE` and `song_page()` in `tools/build_site.py` too. The build stops with a clear message if
one goes missing.

## Play together on the website (2026-11-10)

- No class code (Janelle: "is it necessary to have to type in a student code?"; she's fine with anyone on the same
  piece seeing it). Every song page is one room and joins it by itself 1.5 s after loading. While a teacher conducts
  that piece, a small "Follow" appears at the top of the music, left of Print ("Following", teal, once on; tap to
  stop). Nothing follows unless it is tapped. The teacher signs in from the About box ("Teacher? Sign in to
  conduct", with her violin-studio email and password, her studio app's account); signed in, "Conduct" is in the
  strip on her device only, and the box has "Start conducting" and "Sign out". The first version (same day) had a
  class code typed into a "Play together" box; its saved code is cleared.
- Backend: her Supabase project `violin-studio` (wjzzdiuenlisxueaxqjq), Realtime only. `public.conduct_classes`
  lists who may conduct (its `code` column is no longer used). Each song is two private channels: `conduct:<slug>`,
  where only a listed teacher may send (policies on `realtime.messages` check it), and `conduct-in:<slug>`, where
  anyone may send presence and clock pings. So a student can't move anyone's music. The teacher says she's
  conducting every 2 s on her channel; a follower drops her after 7 s of silence.
- The publishable key is in `app/together.js` on purpose (it is public; the database rules guard everything).
  supabase-js is 2.118.0 from jsdelivr. Offline, a page has no room and tries again when the internet comes back.
- Free plan limits: about 200 devices at once (every open song page is one) and 100 messages a second for the
  project; a class of 20 uses about 40 a second while playing. `eventsPerSecond: 60` lifts the script's own limit
  of 10 a device (with 10, a second student starting to follow at once missed the start).
- Changing songs (Janelle, 2026-11-10: "when the conducting device switches songs, it will switch for everyone else if
  they press follow ... even if they are on the home page"). The teacher's conducting carries on from page to page in
  her tab (sessionStorage `gsa-conduct`) until she taps "Conducting" (or "Stop" on the home page); every page, the home
  page too, listens on `conduct:__site`, where her device says every 2 s which song it has open (none on the home page).
  Tapping Follow keeps a tab following (`gsa-follow`) until "Following" is tapped, the teacher stops, or she isn't heard
  for 10 s: when she opens another song the tab goes there and follows by itself once its player is ready. The home
  page shows a small Follow at the top right while she conducts (which takes the tab to her song), "Following, waiting
  for the teacher to choose a song" while she is on the home page, and on her device "Conducting: open a song · Stop".
  A song page that isn't her song shows the same small Follow at the top while she conducts anywhere (Janelle,
  2026-11-10: "followers ... see the follow button if they are on another song"); tapping it takes the tab to her song.
  Janelle chose to keep the tap card (2026-11-10) over driving a follower's music from the teacher's timing without sound.
  A phone or iPad keeps a new page's sound asleep until it is touched, and the music can't move until then, so the
  page shows a big "Tap to follow your teacher" card; any tap wakes it and catches up. (Headless Chromium never
  sleeps; the test fakes it with a wrapped AudioContext.) A follower that arrives and asks the time before the teacher's
  device has seen it arrive is answered anyway, and asks again every 3 s until answered (it once never lined up).
- Patchy connections (Janelle tried it on her phone's hotspot, 2026-11-12: "very glitchy"). It needs the internet on
  every device (no internet: each device plays on its own, and Follow doesn't appear). A phone's connection is slow and
  uneven and freezes for seconds at a time, so messages come late, in bunches, or (when the connection is made again) not
  at all. So: every command carries `ver`, a number that goes up with each change, and the teacher's reports (`pos`,
  twice a second while playing, every 2 s while stopped: `st` 'moving' or 'still', none while starting, counting in or
  between passes of a loop) carry it with the whole state (tempo, bars, count-in, where). A student that sees a newer
  `ver` than its last command missed one and catches up from the report (`catchUp`); two reports in a row where the
  teacher moves and the student doesn't (or the other way) do the same. A student ignores a command it already had: the
  teacher sends her latest one again whenever someone starts following, and until then the others started over from it
  (back to where Play was pressed, at the tempo then: seen even on good Wi-Fi). In a loop a student goes round by itself
  too, so it doesn't sit at the loop's end waiting for a late word. A student keeps following through 25 s of silence
  (others drop the teacher after 7 s), and a following tab keeps following through 30 s on `conduct:__site`; after a
  reconnect `app/together.js` tracks presence again (supabase-js doesn't). A report that seems to arrive before it was
  sent moves the student's idea of the teacher's clock up (its pings met a slow patch). Checked with a stand-in for
  Supabase that delays, bunches and drops messages per device (Wi-Fi, hotspot, and freezes of 3 to 9 s), with a teacher
  and two students: Play, Pause, tempo, a second student joining, a loop.
- Tests use their own channels (`conduct:test-...`) when localStorage has `gsa-together-test` (tests/smoke.py sets it):
  on 2026-11-10 a local test on Silent Night met Janelle conducting it on the live site, and its students followed her.
- Testing needs a teacher account: make a throwaway one in `auth.users` with a row in `conduct_classes`, and delete it
  afterwards (done that way on 2026-11-10).

## Sight-reading (round 1, 2026-11-12)

A page of endless reading exercises tied page by page to the sight-reading book Janelle is writing, for Suzuki violin
and viola students moving from ear to page: https://graded-string-arrangements.vercel.app/sight-reading/ . Each book
page introduces one note or idea; its QR code will open that page here (`/sight-reading/?page=v1-05`), and the
generator makes new exercises from only what the student has learned so far. The plan for the later rounds (look ahead,
flash a bar, the mic listening, duets, book codes) is in Janelle's brief, which stays out of this public repo.

- Unlisted until Janelle says it's ready: no home-page card or tab, and `noindex` for search engines. It is in the offline
  copy, so it works without the internet after one visit.
- The page is the reader, built by `tools/build_site.py` (`sight_reading_page`) from `reader/reader.html` like a song
  page, so every reader setting works there. Instead of fetching a score it takes MusicXML from `window.readerScore`
  (set by `practice.js`); New exercise and Violin / Viola hand it new music with `reader.newScore(bytes)`, which keeps
  the settings, the size and the loaded sounds. Another book page is a new address (Back returns), since each page has
  its own written tempo (`BASE_TEMPO` comes from `window.sightReading.tempo`).
- A row over the music: the book page (a list), Violin / Viola, the exercise number (type one to bring it back), and a
  big New exercise. On a phone turned sideways (no title) it is pinned along the top beside "All songs", and the reader
  keeps the music below it (practice.css makes `#topInset` taller by the row's height).
- Same page and number, same music on every device (seeded random numbers), so a teacher can put one exercise on every
  stand. The address carries both (`?page=v1-02&n=4821`). The Exercise box in the row is on trial (Janelle, 2026-11-12:
  "I'll leave it for now ... we'll remove it if I don't end up using it"); without it the number would still be in the
  address, on the title card and on printed copies. Violin and viola with one number get the same exercise a fifth
  apart. The instrument is kept on the device (`localStorage` `sight-reading`), not in the address, so one link works for
  both. Changing the generator changes what a number plays: fine while the pages are placeholders, but once the book is
  out a change to the rules should keep the old numbers' music or be a deliberate choice.
- The parts are named `Violin — Sight-reading` / `Viola — Sight-reading`, the reader's one-line layout. Viola in alto
  clef. String colors on the note and its head, finger numbers in `<fingering>` the way her scores write them: a plain
  number where the finger usually sits in first position (1 a whole step above the open string, 2 a major third, 3 a
  fourth, 4 a fifth), an arrow only where it moves (↓1, ↓2, ↑3, ↓4, ↑4). Checked against every fingering in `songs/`
  (2026-11-12); `../BUILD-SPEC.md` and her `add-colors-fingerings.py` were not in the cloud session, so check them
  against those on her PC.
- Decisions (Janelle, 2026-11-12, "go with the suggestions"): what shows on the notes is set by each book page
  (`help`), starting with string colors on and finger numbers and note names off ("Plain notes"); the student can change
  it, and it resets when they open another book page. Exercises are 4 bars on early pages, 8 later (`bars`). Each page
  starts at the slow end of its tempo range.
- Book pages (`sight-reading/pages.json`, put into the page by the build, kept off the site by `.vercelignore`): the
  rules are described at the top of `generator.js`. Notes are in violin string names (`A3` third finger on A); the viola
  plays the same fingers a fifth lower unless the page gives `viola` notes of its own. Every exercise has each of the
  page's `new` notes or rhythms at least twice. Four placeholder pages for now (open A and E; A string 1-2-3; E string
  1-2-3; quarter rests), marked "(placeholder)"; Janelle writes the real ones in her curriculum's order.
- The repo is public: no book content she'll sell goes in it (page text, answer keys, paid page rules once she decides
  where they live), and no access codes or the tool that makes them.
- How an exercise is made: rhythm first (the second phrase starts with the first phrase's rhythm; the last bar is the
  home note, long, on beat 1), then a chord per bar or half bar (I, IV, V, only those the page's notes can outline; the
  first phrase ends on V, the last goes V to I), then the notes (chord notes on strong beats, mostly steps, any other
  note moving by step on at least one side, a turn back after a leap of a fourth or more, never past `maxLeap`, no string
  crossing to or from an eighth note unless the page says `free`). Half the time the second phrase also starts with the
  first phrase's notes. First listen (2026-11-12, by reading them): nearly every A-string exercise ended "B B | A"; notes
  outside the chord may now skip a third on the far side, and the chords are copied only with the notes.
- Look ahead (round 2, 2026-11-12, on the same pull request as round 1 at Janelle's request; she will put both live
  together): "the eyes are the headlights; the hands are the car". A button in the strip, after the ball, steps Off →
  Level 1 (½ beat) → Level 2 (1 beat) → Level 3 (1 bar); a beat is a dotted quarter in 6/8 (Janelle, 2026-11-12: "three
  levels instead"; it began as Off, ½ beat, 1 beat, 2 beats, 1 bar, named by the amount, and a saved "2 beats" becomes
  Level 2). While the music plays, each note vanishes that long before it sounds, with everything on it (head, stem, its part of a beam, finger number, note name, its counts);
  the staff lines, bar lines, clef and key stay, and the ball (or, with the ball off, the cursor) always shows where the
  hands are. Timed to what is heard (`heardTick`: the picture's clock that waits for the speaker, and during a count-in
  the clicks as they are heard). The notes come back when the music stops. Turning it on brings a count-in (Count-in
  only, or On + count-in if the metronome was on) and the written tempo (the book page's slowest); the student can
  change both after. How: `buildLook` measures each note's left edge (its head or rest, its sharp or flat, a finger
  number to its left) after a drawing, and `updateLook` grows a paper-coloured cover per line of music and part
  (`.look-layer`, between the counts and the ball) up to the first note not yet due, with copies of the staff lines and
  bar lines on top. Only the sight-reading page has it: `LOOK_AHEAD` in the reader is false, and the build turns it on
  there. Its button: "Look ahead" over "Level 1" on bigger screens; on phones an eye looking right and just the level
  ("1", "2", "3"), since on an iPhone SE turned sideways the strip had no more room (it stays one row there, and at 1024
  wide); a tap's toast says the level and how far ahead in words ("Look ahead, level 2: each note vanishes one beat before
  you play it"). Round 5's duets will cover only the student's own part.
- Flash a bar (round 3, 2026-11-12, same pull request; Janelle: "Start round 3"): `/sight-reading/flash/?page=v1-02`, opened
  by a "Flash a bar" button in the sight-reading row ("Flash" on a phone turned sideways), on the same book page and
  instrument (they share `localStorage` `sight-reading`). A lighter page than the reader, as the brief suggested: one card
  with the pattern drawn by alphaTab (no player: no sound bank to load), the string colors as the page's `help` says,
  plain notes; three big buttons that never move (Not yet, Start, Got it; greyed out when they don't apply); the streak
  (a star, "in a row", and the best); the level with − and +. A round: the pattern shows (a bar along the bottom runs
  down), hides, shows again on two-look levels, then one bar of clicks (Web Audio, the first higher; the numbers wait for
  the speaker) counts in "Listen… 1 2 3", "Ready… 4", then "Play!" with the beat flashing yellow and no clicks for as long as
  the pattern lasts, then the pattern comes back and the student taps Got it or Not yet. Levels: each length (half a bar,
  shown in 2/4, in 4/4 only; one bar; two bars), and at each 3 s with two looks, then 3 s, 2 s and 1 s with one look
  (12 levels in 4/4). Three Got its in a row move up a level ("Level up!"); Not yet starts the streak again. Level,
  streak and best are kept per book page on the device (`localStorage` `sight-reading-flash`). Tempo: the page's
  slowest. Patterns come from the generator's pattern mode (`SightReading.pattern`): a run of steps one way, a scale
  fragment that turns once, steps with one skip and a step back, or a repeated rhythm (open strings only manage skips
  and repeated rhythms), from the page's notes and rhythms (never a whole note, never starting with a rest), with one of
  its new notes when it can; `noRepeats` (never the same note twice in a row) is there for round 4's listening, with no
  switch on the page yet. Tests set `gsa-flash-fast` in `localStorage`, which makes every wait ten times shorter.
- Listen (round 4, 2026-11-12, same pull request): a "Listen" button (a microphone) on Flash a bar, under the big
  buttons; on, it says "Listening", in teal. The microphone is asked for on that tap (on an iPhone or iPad also on Start
  with Listen already on), without echo cancellation, noise suppression or automatic loudness, which mangle a violin's

## The app version (home screen, offline)

Added to a home screen ("Install the app" in Chrome, Edge and Android; Share, then Add to Home Screen
on iPhone and iPad), the site opens like an app. After one visit every song works with no internet.

- The offline part lives in `app/app.js` and `sw.js`, wired in by the build. The reader itself has no
  app code, so `reader/reader.html` and the Claude preview are untouched. Keep it that way: the same
  layer will be reused for the app-store versions (Google Play, then the App Store through
  Capacitor), where `app/app.js` skips the offline copy because the app carries its own files.
- What is kept offline: the home page, every song page and score, the Bravura font, the string
  sounds, the icons, alphaTab from jsdelivr, and the Google Fonts lettering (Latin letters). About 8 MB
  with two songs. Each new song adds its score (1 to 3 MB). Once that passes about 50 MB, switch to
  keeping only the songs a student has opened.
- Updates: the build writes a fingerprint of every file into `sw.js`. After a push, an installed copy
  picks up the change the next time it is opened online, and downloads only the files that changed
  (a new song doesn't re-download the 4 MB of sounds). Pages come fresh from the network when it
  answers within 3.5 seconds, so a new song shows up on the home page straight away.
- Score, font and sound addresses carry their fingerprint (`?v=...`), so a page never mixes an old
  score with a new page.
- iPhone: `navigator.audioSession.type = 'playback'` lets the music play with the ringer switch off
  (iOS 17 and later). Older iPhones stay silent on mute; there's nothing more to do there without a
  native app.
- App icon: the white note on teal (`assets/icon-*.png`, `assets/apple-touch-icon.png`), the same as
  the browser-tab icon. Janelle chose it over a design with the open strings in their colors (2026-10-16).
- `sw.js` lists every song page's fingerprint. When sessions commit separately, whoever commits second
  rebuilds and commits `sw.js` with the song pages.
- The Claude desktop browser pane supports offline copies. Use the `website-app-8030` entry in
  `../.claude/launch.json`: the other entries hard-code ports that other sessions are often using.
